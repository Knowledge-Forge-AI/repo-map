## Context

MCP-OPS1 through MCP-OPS5 turned ADR 0031 into useful local operations
prototypes: a TOML config loader, graph registry readback, graph refresh, an
expanded read-only MCP surface, and a read-only server-memory bridge.

Those phases also kept ADR 0031's early local-runtime assumption: RepoMap would
read a single operations config file such as `repomap.local.toml` and talk to a
direct localhost Postgres profile. That was useful for proving the operations
surface, but it is not the intended end-user runtime model.

RepoMap's local operations environment should be isolated from the user's
normal machine environment. RepoMap must not assume that the user has a
directly installed local Postgres server, must not create databases on a
preexisting user-visible Postgres server by default, and must not reserve
standard localhost ports such as `5432`.

The corrected target is a local containerized runtime cluster:

- a RepoMap server/MCP container;
- a Postgres container owned by RepoMap;
- explicit local volumes associated with `REPOMAP_HOME`;
- configurable localhost port mappings; and
- no public tunnel or remote database exposure by default.

Configuration also needs correction before more private operational dogfooding.
Because the local operations surface is not yet externally depended upon,
RepoMap can change its target ops/MCP config design now instead of carrying
compatibility constraints that fight the desired local product.

MCP-RUNTIME0 is architecture and documentation only. It does not implement a
new config loader, remove JSON code, start containers, create Dockerfiles,
change tests, read private local paths, create home-directory config, edit
server-memory, edit policy files, open tunnels, add web UI, or proceed to
MCP-OPS6.

## Decision

RepoMap's permanent local operations target is a containerized local runtime
managed from a configuration home:

```text
REPOMAP_HOME
-> TOML config folder (*.rp.toml, *.rpl.toml)
-> local runtime metadata and generated runtime artifacts
-> containerized RepoMap server/MCP process
-> containerized Postgres storage
-> read-only MCP/CLI readback over configured graphs
```

The target runtime replaces the direct-host-Postgres posture in ADR 0031 for
end-user local operations. ADR 0031 remains valid for the higher-level product
shape: graph registry, read-only MCP surface, refresh boundaries,
server-memory relationship, privacy posture, operational policy dogfooding, and
destructive-operation exclusions. ADR 0032 supersedes ADR 0031 only for local
runtime, config-home, ops-config format, and test-harness details.

## Scope

In scope:

- containerized local RepoMap runtime architecture;
- `REPOMAP_HOME` semantics;
- TOML config-folder model;
- `*.rp.toml` and `*.rpl.toml` file semantics;
- autogenerated `repomap.rpl.toml` local setup config;
- removal of JSON ops/MCP registry config from the new target design;
- containerized Postgres runtime posture;
- containerized RepoMap server/MCP runtime posture;
- configurable non-standard localhost port mappings;
- integration-test Postgres container harness architecture;
- path exclusion configuration for folder-tree-backed graphs; and
- future implementation phases before MCP-OPS6.

Out of scope:

- implementing the new config loader;
- removing existing JSON code;
- creating container definitions, Dockerfiles, or compose files;
- starting containers;
- changing test harness code;
- changing MCP server runtime code;
- implementing path exclusions;
- creating real local config under a home directory;
- reading `~/.codex`, `~/.repo-map`, `~/.flakes`, or other private roots;
- running Docker, Podman, Colima, or other container tools;
- opening tunnels;
- adding web UI;
- adding destructive database operations;
- mutating server-memory;
- editing `codex-vc/AGENTS.md`; and
- proceeding to MCP-OPS6.

## Hard Guardrails

MCP-RUNTIME0 must not:

- implement code;
- read private local paths;
- create local config files in the user's home directory;
- start containers;
- expose standard Postgres port `5432` by default;
- expose standard MCP or server ports by default;
- assume Docker Desktop specifically when Docker-compatible, Podman, or
  Colima-compatible wording is practical;
- expose Postgres remotely;
- add database drop, clear, truncate, reset, or wipe behavior;
- mutate server-memory; or
- edit private operational policy files.

Future implementation phases must preserve those guardrails unless a later ADR
accepts a narrower exception.

## Product Posture

MCP-RUNTIME0 is not "build the runtime." MCP-RUNTIME0 is "correct the local
runtime and configuration architecture before more private operational
dogfooding."

RepoMap local operations should be isolated from the user's host environment:

- RepoMap owns its local runtime containers;
- RepoMap owns its local Postgres container and volume;
- RepoMap uses an explicit config home;
- RepoMap ports bind to localhost only by default;
- no standard host port is assumed;
- no host-installed Postgres is required; and
- no user preexisting database is used silently.

## Containerized Local Runtime

The future local runtime cluster has at least two containers.

`repomap-server`

- runs the RepoMap server and MCP process;
- reads configuration from a mounted `REPOMAP_HOME`;
- talks to Postgres over the internal container network;
- exposes MCP/server access only through configured local transport or
  localhost port mapping;
- does not bind publicly by default;
- does not start a web UI unless a later ADR accepts that scope; and
- does not open tunnels.

`repomap-postgres`

- stores RepoMap data only;
- uses a RepoMap-managed volume associated with `REPOMAP_HOME`;
- does not reuse host-installed Postgres;
- does not bind to `localhost:5432` by default;
- exposes a configurable localhost-only mapped port for diagnostics or DBeaver
  when enabled; and
- uses local runtime credentials, not the user's system credentials.

The cluster may later be implemented with Docker-compatible CLI semantics while
remaining open to Podman or Colima where practical.

## Port Posture

No container should assume a standard host port.

Rules:

- Postgres must not map to `localhost:5432` by default.
- RepoMap server/MCP must not assume a standard host port.
- Host port mappings must be explicit and configurable.
- Defaults should use high, unlikely-to-conflict localhost ports.
- If a port is occupied, startup should fail with a clear diagnostic unless a
  later phase explicitly implements a documented fallback.
- Ports must bind to localhost only by default.
- No public listen address is allowed by default.

Recommended future defaults:

- Postgres host port: `55432`.
- RepoMap server HTTP or local MCP host port, if TCP is used: `55880`.
- MCP stdio transport remains portless when selected.

These are recommendations for implementation, not current behavior.

## Postgres Credentials

Local container credentials belong to the isolated RepoMap runtime.

Policy:

- prefer generated credentials or a local ignored env/secret file;
- committed examples should use env references or placeholders;
- `admin/admin` is acceptable only in clearly marked local isolated dev
  examples and must be described as unsafe outside localhost/container dev;
- DBeaver access should target the configured mapped localhost port; and
- credentials must not appear in committed examples, diagnostics, MCP
  responses, logs, status docs, raw observations, or canonical metadata.

RepoMap must not expose Postgres remotely and must not recommend connecting a
public tunnel to Postgres.

## REPOMAP_HOME

`REPOMAP_HOME` is the local operations/config root.

Definition:

- environment variable: `REPOMAP_HOME`;
- default: `~/.repo-map`;
- intended path on the user's machine: `~/.codex/.codex-vc/mcp/repo-map`;
- contains TOML config files, local runtime metadata, generated runtime
  artifacts, logs/status where applicable, and container volume references;
- should not be committed to the public RepoMap repository; and
- must not leak private paths or secrets into public status docs or examples.

Implementation should expand `~` only for local runtime use and redacted status
display. Config validation must not read private roots unless an explicit
command requires it and the graph/source is enabled.

## TOML Config Folder Model

Configuration is discovered from `REPOMAP_HOME` as a collection of TOML files.
The target design replaces the single-file `repomap.local.toml` and
`repomap.toml` model.

Supported file extensions:

- `*.rp.toml`
- `*.rpl.toml`

`*.rp.toml`

- project or shareable RepoMap configuration;
- should not contain local secrets;
- replaces old `repomap.toml` semantics; and
- may define shareable graph/source defaults, extractor profiles, and project
  policy.

`*.rpl.toml`

- local/private RepoMap configuration;
- may contain machine-specific paths and local runtime settings;
- replaces old `repomap.local.toml` semantics; and
- may overlay local graph enablement, privacy choices, runtime ports, and
  secret references.

Autogenerated local setup config:

```text
repomap.rpl.toml
```

The config folder is intentionally modular. RepoMap should not require one
giant hand-authored file.

## Config Merge And Diagnostics

Future config loading should:

- support `schema_version = 1`;
- load `*.rp.toml` first;
- load `*.rpl.toml` second as local/private overlays;
- sort files lexicographically within each extension class;
- merge deterministically;
- report duplicate graph ids;
- report duplicate source ids;
- report conflicting runtime settings;
- report unknown sections;
- report unsupported schema versions;
- redact secret-like values in diagnostics; and
- preserve enough source-file attribution to explain conflicts.

`*.rpl.toml` may override `*.rp.toml` for explicitly local settings such as
enabled flags, MCP visibility, root paths, local ports, local secret references,
and refresh policies. Ambiguous conflicts should produce diagnostics rather
than silent behavior changes.

## JSON Ops Config Removal

The new target design removes JSON ops/MCP registry configuration from the
local operations path.

Policy:

- backwards compatibility with the old ops/MCP JSON registry config is not
  required for the corrected local runtime target;
- future implementation may remove JSON registry/config support for the
  ops/MCP path;
- historical JSON source ingestion, JSON document extraction, and JSON
  artifact support are unrelated and must remain intact unless separately
  changed; and
- docs and diagnostics should distinguish "ops config JSON removal" from
  "JSON extraction/source support."

Existing feed, GitHub, and documented API configs should migrate structurally
into the `REPOMAP_HOME` TOML folder model. Because those configs are already
TOML, the migration is a section/layout migration, not a format change.
Config loading must not fetch feeds, call GitHub, call documented APIs, or
perform acquisition.

## Folder-Tree Graph Exclusions

Folder-tree-backed graphs need explicit configured exclusions before private or
noisy roots are refreshed.

Future graph config should support:

```toml
[[graphs]]
id = "flakes"
root_path = "~/.flakes"
enabled = true

exclude_paths = [
  ".git",
  ".serena",
  ".venv",
  "__pycache__",
  ".pytest_cache",
  "node_modules",
  ".terraform",
  "result",
  "result-*",
  "secrets.local",
]
```

Rules:

- exclusions may name individual files or directories;
- exclusions are interpreted relative to graph root unless a later ADR accepts
  absolute exclusions;
- traversal outside the graph root is invalid;
- excludes apply before discovery or refresh reads files;
- graph status/readback should expose counts or bounded summaries of excludes;
- excludes must not leak secret path contents;
- existing default discovery excludes remain in force; and
- user-defined excludes add to defaults unless later configuration explicitly
  accepts replacement semantics.

## Containerized Integration-Test Postgres Harness

The current integration harness uses temporary host Postgres clusters and needs
host IPC access in sandboxed Codex runs. ADR 0032 replaces that target with a
temporary containerized Postgres harness.

Target behavior:

- the integration test runner starts a temporary Postgres container at the
  beginning of an integration run;
- tests use that container for storage-backed integration tests;
- teardown runs on success and failure where practical;
- the harness does not depend on host-installed Postgres;
- the harness does not require host IPC;
- the harness does not use a user's preexisting Postgres server;
- the default host port is high and unlikely to be in use;
- the port is configurable;
- tests do not require port `5432`;
- tests do not leave persistent containers or volumes by default;
- the container runtime is detected or explicitly configured; and
- Postgres binds to localhost only.

Future runner arguments may include:

```sh
python3 tools/run_tests.py --suite int --pg-container-port 55432
python3 tools/run_tests.py --suite all --pg-container-port 55432
```

Possible later options:

- `--pg-container-runtime docker|podman`;
- `--reuse-pg-container`, only if explicitly accepted later; and
- `--keep-pg-container-on-failure`, only if explicitly accepted later.

If no container runtime is available, the integration suite should fail or skip
with a clear diagnostic according to a documented suite policy. The harness
must avoid privileged containers and remote database exposure.

## Server Container

The future RepoMap server container should:

- be built from local source or a packaged image;
- run the RepoMap server/MCP process;
- read the mounted `REPOMAP_HOME`;
- use the internal container-network Postgres host and port;
- map an external localhost MCP/server port only when needed;
- avoid public binds by default;
- avoid standard port defaults; and
- make local transport choice explicit.

## Local Setup Commands

Future commands may include:

```sh
repomap-kg local setup
repomap-kg local up
repomap-kg local down
repomap-kg local status
```

The commands are not implemented in MCP-RUNTIME0.

Future behavior should:

- create `REPOMAP_HOME` when missing;
- generate `repomap.rpl.toml` when missing;
- generate a local env/secret file when needed;
- start the container cluster;
- report configured localhost ports;
- show DBeaver connection information for the containerized Postgres only;
- avoid destructive actions; and
- avoid overwriting existing config without backup or confirmation.

## Destructive-Operation Posture

RepoMap product and MCP surfaces must still not include:

- drop database;
- clear database;
- truncate tables;
- reset all data;
- wipe graph;
- delete configured graph;
- delete all observations;
- delete all canonical nodes.

A later local runtime command may stop or remove containers that RepoMap
created. That is container lifecycle management, not graph data deletion. It
should preserve volumes by default unless a later destructive-operation phase
explicitly accepts volume deletion with dry run, backup/export guidance,
confirmation, and audit trail.

ADR 0033 supersedes this section for database lifecycle architecture. It keeps
ordinary MCP/server access non-destructive, but defines a backup-first local
administrative model for future dump, restore, initialization, and database drop
commands scoped to RepoMap-owned containerized databases.

## Relationship To MCP-OPS1 Through MCP-OPS5

MCP-OPS1 through MCP-OPS5 remain valuable prototypes and may continue to exist
until the runtime correction lands in code. Their command shapes and docs are
not retroactively edited in MCP-RUNTIME0 except for ADR 0031's supersession
note.

Future implementation should migrate:

- single-file `--config repomap.local.toml` flows to `REPOMAP_HOME` config
  folder resolution;
- direct local Postgres profiles to container runtime profiles;
- JSON ops/MCP registry support out of the local operations target;
- host-IPC temporary Postgres tests to a containerized test harness; and
- graph refresh to apply configured `exclude_paths` before reading roots.

## Network And Tunnel Posture

The preferred deployment is local-only.

Defaults:

- MCP/server transport is stdio or localhost-only;
- Postgres binds to localhost only when mapped to the host;
- containers communicate over an internal local network;
- no public tunnel is opened;
- no remote Postgres is exposed;
- no dev credentials are exposed beyond the local isolated runtime; and
- no web UI is started.

Remote access remains a separate security-review phase. That phase should
prefer least privilege, authentication, audit logging, and controlled MCP/API
exposure. It must never expose Postgres directly.

## Future Tests

Future implementation phases should add tests for:

- `REPOMAP_HOME` defaulting and explicit override;
- `*.rp.toml` and `*.rpl.toml` discovery;
- deterministic merge order;
- local overlay behavior;
- duplicate graph/source diagnostics;
- conflicting runtime setting diagnostics;
- secret redaction in config diagnostics;
- generated `repomap.rpl.toml` template safety;
- removal of JSON ops config from the local ops path;
- preservation of JSON extraction/source artifact behavior;
- graph `exclude_paths` validation;
- exclusions applied before discovery reads files;
- containerized Postgres harness startup and teardown;
- configurable `--pg-container-port`;
- no use of host port `5432` by default;
- clear diagnostics for occupied ports;
- clear diagnostics for missing container runtime;
- no host-installed Postgres dependency;
- no host IPC requirement;
- no user preexisting database access;
- no public bind;
- no destructive database behavior; and
- no private-root reads during config validation.

## Future Phases

`MCP-RUNTIME1: REPOMAP_HOME TOML config folder implementation`

- implement `REPOMAP_HOME` defaulting;
- load `*.rp.toml` and `*.rpl.toml`;
- implement deterministic merge and local overlays;
- generate or validate `repomap.rpl.toml` templates;
- remove JSON ops/MCP registry config from the local ops path;
- preserve JSON extraction/source data support;
- parse graph `exclude_paths`; and
- update ops config-check, graphs, refresh, and MCP commands to use the config
  folder.

`MCP-RUNTIME2: Containerized local runtime`

- add container definitions for RepoMap server and Postgres;
- add local setup/up/down/status commands;
- support configurable localhost port mappings;
- handle local env/secret files;
- report DBeaver connection information for the containerized Postgres; and
- avoid destructive database wipe behavior.

`MCP-RUNTIME3: Containerized integration-test Postgres harness`

- replace the host-IPC temporary Postgres harness with a temporary container;
- add `--pg-container-port` to `tools/run_tests.py`;
- start and tear down the container automatically;
- provide diagnostics for missing container runtime or port conflicts; and
- avoid persistent containers/volumes by default.

`MCP-RUNTIME4: Graph exclude_paths enforcement`

- apply graph `exclude_paths` before discovery or refresh;
- support file and directory exclusions;
- test private and noisy graph exclusions; and
- report bounded exclude summaries in graph status/readback.

`MCP-RUNTIME5: Backup-first database lifecycle`

- define dump and dump-all behavior;
- define initialization from source and dump;
- define database drop only after mandatory pre-drop backup;
- define direct Postgres host-port exposure as a dev/debug opt-in; and
- keep ordinary MCP/server access API-first and non-destructive.

Then resume:

`MCP-OPS6: Operational policy dogfooding`

- proceed only after runtime/config isolation is corrected;
- inspect private policy evidence only with user-approved tooling; and
- avoid leaking private operational policy content into public RepoMap commits.

## Rejected Alternatives

Rejected:

- continuing to target a host-installed local Postgres server;
- creating RepoMap databases on a user's preexisting Postgres by default;
- using `localhost:5432` as the default Postgres port;
- assuming standard MCP/server ports;
- preserving JSON ops/MCP registry config as a required compatibility target;
- keeping `repomap.local.toml` as the target local ops config name;
- treating one large TOML file as the only supported config model;
- running integration tests through host-IPC temporary Postgres clusters as the
  future target;
- requiring Docker Desktop specifically in the architecture;
- exposing Postgres remotely;
- opening tunnels automatically;
- starting a web UI track; and
- proceeding to MCP-OPS6 before runtime/config isolation is corrected.

## Consequences

Near-term consequences:

- ADR 0031 is superseded in part for local runtime and config-home details.
- MCP-OPS1 through MCP-OPS5 are treated as useful prototypes whose target
  config/runtime assumptions now need migration.
- MCP-RUNTIME1 should land before container work because the config model needs
  to stop fighting the intended runtime.
- MCP-OPS6 should wait until the local runtime/config isolation is corrected.
- Future docs and examples should use `REPOMAP_HOME`, `*.rp.toml`,
  `*.rpl.toml`, and `repomap.rpl.toml` terminology for local operations.

## Acceptance

MCP-RUNTIME0 is accepted only if it clearly supersedes the host-Postgres and
single-file local config assumptions while defining:

- containerized local runtime;
- `REPOMAP_HOME` config folder;
- `*.rp.toml` and `*.rpl.toml` semantics;
- autogenerated `repomap.rpl.toml`;
- removal of JSON ops config from the target local operations design;
- configurable non-standard localhost ports;
- temporary containerized Postgres integration-test harness;
- graph `exclude_paths`; and
- non-destructive local operations posture.
